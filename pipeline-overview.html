5 Layers — Options & Tradeoffs

From research §2-6

◍ Ingestion push/stream/CDC

  • Webhooks/REST — <100ms, low-med throughput, low ops. 50 LOC FastAPI. Svix for retries.
  • Kafka/Redpanda — <10ms, 1M+/s, high ops unless managed. Redpanda: single binary, 10x simpler. Use Confluent/Upstash cloud.
  • Kinesis — ~200ms, 10k/shard/s, low ops. AWS-native, 7-day retention. Use if AWS-only & <100M/d.
  • PubSub / SQS+SNS — 50-500ms, auto-scale infinite, very low ops, per-msg. Best starting queue for small team. SQS→Lambda→S3 covers 80%.
  • CDC — Debezium OSS gold (PG WAL→Kafka) but needs Kafka Connect. Airbyte/Fivetran managed CDC zero ops.
  • Batch — Airbyte/Fivetran for external APIs. Don't build connectors unless proprietary.
Start: FastAPI+SQSGrowth: Redpanda CloudAnti: Kafka too early

◑ Storage OLTP / lake / warehouse

  • Postgres (Neon/Supabase/RDS) — OLTP, ms latency, $10-50/mo. Handles 100M rows with JSONB, pg_cron. OLTP longer than you think.
  • S3/GCS — infinite, secs via query engine, $0.023/GB, zero ops. Always land raw s3://raw/YYYY/MM/DD/ immutable.
  • BigQuery — serverless, auto-scale, $5/TB queried, free tier. Best small team, pay-per-query. Partition to avoid surprises.
  • Snowflake — governed enterprise, $2-4/credit min $200+. Separation compute/storage.
  • DuckDB — embedded OLAP, free, zero ops, queries parquet directly. 100M rows on laptop. Use as transform engine before warehouse.
  • Lakehouse — Delta (Spark), Iceberg (open, multi-engine), Hudi (upserts). Start parquet, Iceberg when need time-travel > trillion rows.
Source of truth: S3Anti: Snowflake at 1k/dR2 cheaper egress

⧉ Transform batch & streaming

  • Python Polars/DuckDB — <10GB single node, zero ops. Polars 10x pandas. Processes 100M rows laptop.
  • DBT — must-use for warehouse. SQL+Jinja, tests, docs, lineage. Core free, Cloud for CI. Don't build transform framework.
  • Spark — TB-PB, high ops. Only >100GB shuffle. Most startups premature; avoid until 100M+/day & transforms >1hr.
  • Flink / Bytewax / ksqlDB — streaming stateful. Flink complex (RocksDB+S3 checkpoint). Small team: micro-batch 1-min or RisingWave/Materialize Python-friendly.
<1GB: Polars1-100GB: DBT+BQStreaming: Bytewax

↻ Orchestration scheduling

  • Cron+Python — single node, zero ops, works surprisingly long. GitHub Actions cron / pg_cron.
  • Airflow — DAG standard, rich UI old, large scale Celery+K8s, high ops, high learning. 1000+ operators. Choose if hiring pool needs it.
  • Dagster ⭐ — asset-based, software-defined, modern lineage, excellent UI, low-med ops. Local dagster dev instant. Best tradeoff small→mid.
  • Prefect 2 — Pythonic @flow/@task minimal boilerplate, Cloud free generous. Easiest Python devs.
  • Temporal — durable execution, never lose job. For business processes (payments) over days, not ELT.
  • Step Functions — zero ops AWS glue S3→Lambda→Warehouse, JSON verbose.
Start: Cron/PrefectGrow: DagsterDurable: Temporal

◎ Observability logs / metrics / traces / data quality

Core Signals
  • Logs: Loki/ELK/CloudWatch → Datadog/BetterStack free-$50
  • Metrics: Prometheus+Grafana → Datadog/Grafana Cloud
  • Traces: OTel+Jaeger/Tempo → Honeycomb
  • Data Quality: DBT tests/GE/Soda → Monte Carlo/Bigeye $10k+/yr only at 100M+
  • Alert tiers: T1 pipeline fail, T2 freshness lag, T3 quality anomaly, T4 cost spike
OTel Non-negotiable
  • Standard for traces/metrics/logs
  • Instrument FastAPI opentelemetry-instrumentation-fastapi, psycopg
  • Send to Grafana Cloud free 10k series or Jaeger
  • Structure logs JSON include trace_id, pipeline_run_id, event_count
  • S3 access logs for audit
Data Observability Unique
  • DBT tests: uniqueness, not_null, accepted_values — free
  • Great Expectations / Soda heavier but good
  • Monte Carlo only when data downtime cost > tool cost
  • Build DBT tests manually, buy Monte Carlo later

Users · Products · Events · Purchases — realistic funnel for pipeline research

Business scenario: Online retailer wants shopper behavior browsing→checkout. Analysts ask converting? referrer revenue? device/category? funnel drop-off? Product asks personalization, cart-abandon nudge, daily revenue dashboard. Dataset synthetic, RFC2606 emails, seed 42.

Recommendations — What to Build vs Buy

⚒ Build manually — high learning, high control, low ops risk

  1. Webhook receiver + validation — 1 FastAPI route Pydantic, idempotency pattern
  2. Simple queue consumer — PG FOR UPDATE SKIP LOCKED or SQS polling loop, ack/retry
  3. Raw→staging DuckDB/Polars — own business logic, avoid black-box
  4. DBT models + tests — data model core IP never outsource
  5. S3 partitioning + Parquet writer — file layout impacts query cost 100x
  6. OTel instrumentation — vendor neutral trace/metrics
  7. Data API serving — FastAPI over DW view
  8. Dead-letter + replay — teaches exactly-once vs at-least
  9. Idempotency keys + dedup — critical not fully solved by tooling

☁ Plug-and-play for speed — low learning value, high ops if built

  1. Kafka hosting — Redpanda/Confluent Cloud, self-host wastes sprints
  2. Postgres hosting/backups — Neon/Supabase/RDS WAL archiving
  3. Warehouse engine — BigQuery/Snowflake never build
  4. Connector ingestion — Airbyte/Fivetran API changes constant
  5. Airflow hosting — Dagster/Prefect Cloud/MWAA scheduler ops thankless
  6. Spark cluster — EMR/Databricks serverless don't tune YARN
  7. Observability backend — Grafana Cloud/Datadog don't run ELK unless expert
  8. Schema Registry, CDC infra — Confluent Registry, Debezium managed
  9. Secret mgmt auth — cloud IAM Doppler

Anti-patterns & Pitfalls

  • Kafka too early — ordering/partitioning bugs for <100k/d
  • No raw landing — no reprocess; always save raw
  • EL vs ELT confusion — don't transform before warehouse early, ELT simpler
  • Spark for small data — 100x cost 10x latency vs DuckDB
  • Airflow as cron — over-engineering <10 DAGs
  • No idempotency — duplicates cause money bugs add idempotency_key unique
  • Manual JSON logs — not queryable use structured+trace_id
  • No partitioning — BQ full scan $100 query partition date cluster user_id
  • Premature exactly-once — aim at-least-once+idempotent consumer first
  • Building connectors — API drift kills buy Airbyte
